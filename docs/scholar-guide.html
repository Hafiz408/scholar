Scholar is a full-stack RAG application: a FastAPI + LangGraph backend over a dual retrieval engine, a Next.js 14 frontend with native SSE streaming, and a RAGAS evaluation harness that benchmarks the retrieval strategies head-to-head. Everything is model-agnostic — the same checkout runs on OpenAI, Anthropic, Google, or any OpenAI-compatible endpoint by editing .env alone.

Getting Started

What Scholar Does

A student uploads course material, says "I want to master this by the 30th," and Scholar runs the full study loop — every note, chat answer, and quiz question grounded in and limited to the uploaded sources.

📤
Bring your own books
Upload PDFs or paste a URL. Text extraction, structural tree-building, and vector indexing are automatic and run in the background.
🎯
Goal-driven plans
Set topic, level, and deadline; a Planner agent generates a session-by-session plan sized to the time you have.
📝
AI study notes
Each session opens with concise, streamed Markdown notes — every claim cited to a source and page.
💬

Ask anything; answers come only from your books, with source citations. History persists across refreshes via a LangGraph checkpointer.

Auto-generated MCQs. A score below 65% automatically inserts a targeted remedial session and renumbers the plan.
🏁

Core Concepts

The vocabulary that runs through the whole codebase. If you understand these eight terms, the rest of the guide reads easily.

retrieval PageIndex
Structural, vectorless retrieval. An LLM builds a hierarchical tree of the document at ingestion; at query time another LLM navigates that tree and returns whole coherent sections.
retrieval Vector
Semantic retrieval. Text is chunked (600/100 tokens), embedded, and stored in pgvector; queries are matched by cosine similarity. Zero LLM calls at query time.
retrieval Hybrid
Runs both concurrently and merges: 0.6·PageIndex + 0.4·vector, de-duplicated by content hash. The empirically best default.
retrieval Router
A lightweight classifier that picks a strategy per query (or short-circuits to vector when no tree exists). Active when RETRIEVAL_STRATEGY=auto.
domain Goal & Session
A goal (topic + level + deadline) expands into N ordered sessions. Sessions unlock sequentially; each has notes, chat, and a quiz.
domain Adaptive learning
Failing a quiz inserts a remedial session right after the current one and atomically renumbers the rest, so a second failure can't corrupt the order.
domain Super Agent
A goal-independent chat that retrieves across every ready source. Keyed by a thread_id the browser owns in localStorage.
infra Checkpointer
LangGraph's AsyncPostgresSaver. Persists conversation state per thread_id so chat survives a browser refresh without a bespoke history table.

Data Flow — Upload to First Cited Note

The end-to-end path a new user travels, and where each piece of state is created.

1
Upload a PDF/URL
POST /knowledge/upload saves the file to data/uploads/{id}.pdf, inserts a knowledge_sources row (status=pending), and returns the source_id immediately. Ingestion runs as a FastAPI BackgroundTask.
2
Background ingestion (4 stages)
Extract text → build PageIndex tree (PDFs) → chunk + embed into pgvector → mark ready. The frontend polls GET /knowledge/{id}/status every 3s and shows the status badge advancing.
3
Create a goal
POST /goals with topic/level/deadline/source_ids. The Planner computes a session count (ceil(deadline_days / 7 × sessions_per_week)) and the LLM returns an ordered plan via structured output. Goal + sessions are inserted into Postgres.
4
Start a session → retrieve
POST /sessions/{id}/start calls retrieve(topic, source_ids, top_k=8). The router picks a strategy; chunks come back ranked, each tagged with source title + page.
5
Stream cited notes (SSE)
The Note Generator formats chunks as a numbered context block, streams Markdown tokens over text/event-stream (notes_chunk events), then persists the full notes and flips the session to in_progress (notes_done).
✓
Learn → chat → quiz → adapt → finish
The student reads, asks grounded questions (history checkpointed by goal_id), takes a quiz, and — on a pass across all sessions — sits the final test that completes the goal.

Stage 1 — Text extraction

  • PDF: pdfplumber primary, falling back to pypdf per-page on failure. Pages with fewer than 20 words are skipped as blank/diagram-only.
  • URL: trafilatura fetches and extracts main text (tables included); page count is estimated at ~300 words/page.
  • Optional vision: if VISION_MODEL is set, PDF pages are rendered at 150 DPI with PyMuPDF and described by a vision LLM; the description is appended as [Visual content: …]. Capped by VISION_MAX_PAGES (default 20; 0=unlimited), with per-page exception isolation.

Stage 2 — PageIndex tree (PDF only)

The open-source PageIndex library builds a hierarchical tree — roughly 140–220 LLM calls for a 58-page book, paid once — and writes it to data/uploads/{id}_tree.json. Each node carries node_id, title, summary, section text, and a page range. On any failure it logs a warning and returns None (vector-only fallback). URLs skip this stage.

Stage 3 — Chunk + embed

A RecursiveCharacterTextSplitter(chunk_size=600, chunk_overlap=100) chunks the pages; chunks are embedded in batches of 50 via the configured embeddings API and upserted into the pgvector knowledge_chunks table with ON CONFLICT (id) DO UPDATE (idempotent re-ingestion).

📈
Status machine: pending → indexing_pageindex → indexing_vectors → ready (or failed). The final row stores pageindex_doc_id = source_id on success, or NULL when the tree build failed — which is exactly what the router reads to decide whether PageIndex is even possible for that source.

Dual Retrieval Engine

Scholar's defining design choice: run two complementary retrievers and route each query to the right one. A single strategy leaves gaps — vector chops structure into 600-token fragments; PageIndex can miss a precise fact buried mid-section. Keep both, let a router choose. Click a strategy:

🌳
PageIndex
structural · vectorless
🧲
Vector
semantic · cosine
⚗️
Hybrid
merged · default

PageIndex — structural retrieval

At query time (one LLM call): the tree is flattened to a compact skeleton of node_id + title + summary, the LLM is asked which node IDs answer the query, and the full text of those nodes is returned. Relevance score is rank-based: 1.0 / (1 + rank). Returns [] on any error rather than raising.

Best for: "what does the unit on climate change cover?" — structural, long-form, navigational questions. Measured strength: highest faithfulness (whole sections give the LLM more grounding context).

Vector — semantic retrieval

The query is embedded and ranked by cosine similarity in pgvector, scoped to the relevant source_ids: 1 - (embedding <=> query) over an ivfflat index. Zero LLM calls at query time, and it works for any source — making it the universal fallback when a document has no tree.

Best for: "define genetic diversity" — factual lookups, cross-book search. Measured strength: highest answer relevancy + context precision, ~700ms faster than PageIndex.

Hybrid — weighted merge

Both retrievers run concurrently (asyncio.gather); results are merged by weighted score and de-duplicated by SHA-256 of chunk content:

hybrid_retriever.pymerge
combined_score = 0.6 × pageindex_score + 0.4 × vector_score # dedup by sha256(content); non-mutating via model_copy() # sorted desc, sliced to top_k

The 0.6/0.4 weighting favors PageIndex's structural coherence while letting vector hits surface precise facts the section-level retrieval might dilute. This is the empirical case for the default.

The Router

When RETRIEVAL_STRATEGY=auto, a classifier picks per query. If no source in scope has a pageindex_doc_id, it short-circuits to vector with no LLM call (the RETR-02 guard); otherwise one structured-output call returns pageindex | vector | hybrid. Forcing a strategy via env skips the router entirely. A test gate requires ≥8/10 correct classifications on a labelled query set.

🐛
A bug worth documenting (the war-story). PageIndex retrieval was historically silently broken, returning zero chunks for nearly every query — so the head-to-head comparison was meaningless. Two causes: (1) the builder set the library's options to Python True, but the library checks them against the string 'yes', so node_id/summary/text were never written to the tree; (2) the retriever read node.id while the library writes node_id. Both fixed; trees built before the fix must be rebuilt by re-ingesting. The lesson: a RAG component can "work" — no errors, valid JSON — while returning nothing useful. You only catch it with evaluation.

Why LangGraph here?

The orchestrator builds a minimal StateGraph with a single pass-through chat node whose only purpose is to give the AsyncPostgresSaver checkpointer a graph to attach to. The conversational agents then read and write history with one config object — no bespoke history table, no manual message-window management:

config = {"configurable": {"thread_id": goal_id, "checkpoint_ns": ""}} # checkpoint_ns="" is required — the default namespace. # session chat → thread_id = goal_id (one conversation per goal) # super agent → thread_id = client UUID from localStorage

Storage Model — Three Stores, by Access Pattern

Scholar uses two storage tiers: a single PostgreSQL instance (with pgvector) for all structured data, and local disk for binary blobs.

Key tables

  • knowledge_sources — id, title, source_type, file_path, url, page_count, pageindex_doc_id, status. The pageindex_doc_id being NULL is the signal for vector-only fallback.
  • study_goals — knowledge_source_ids (JSON array), deadline_days, level, sessions_per_week, status, notion_page_url.
  • study_sessions — session_number, title, topic, status, quiz_score, notes_markdown, quiz_questions (full questions with correct_index stored server-side).
  • cumulative_tests — final-test questions + weak_session_numbers.
  • knowledge_chunks (pgvector) — embedding vector(dims) with ivfflat (embedding vector_cosine_ops) + a source index.
⚠️
EMBEDDING_DIMENSIONS must match the embedding model — the pgvector column is created at that width. Changing it (e.g. 1536 for OpenAI vs 768 for nomic-embed-text) requires a fresh vector store.

Frontend & SSE Streaming

Next.js 14 App Router, TypeScript (strict), Tailwind, react-markdown + remark-gfm, react-dropzone. State is plain React hooks — no Redux/Zustand. A next.config.mjs rewrite proxies /api/* to the backend (skipTrailingSlashRedirect preserves FastAPI's trailing slashes).

The native SSE client

No EventSource library. A small async-generator parser in lib/sse.ts reads the fetch response's ReadableStream, decodes with TextDecoder, buffers partial lines, and yields {event, data} per the SSE spec. Each stream function returns a cleanup that aborts via AbortController (wired into React useEffect cleanup):

lib/sse.tsparseSSE
async function* parseSSE(reader) { const decoder = new TextDecoder() let buf = '', event = 'message' while (true) { const { done, value } = await reader.read() if (done) break buf += decoder.decode(value, { stream: true }) const lines = buf.split('\n'); buf = lines.pop() ?? '' for (const line of lines) { if (line.startsWith('event:')) event = line.slice(6).trim() else if (line.startsWith('data:')) { yield { event, data: line.slice(5).trim() }; event = 'message' } } } }

Three thin wrappers consume it — streamNotes, streamChat, streamSuperChat — each dispatching typed callbacks per event:

event: token {"content": "The sodium-potassium pump…"}
event: token {"content": " maintains the resting potential."}
event: citations {"chunks": [{"source_title": "Biology 2e", "page_number": 1009}]}
event: done {"strategy_used": "hybrid", "latency_ms": 2157}

Pages & the study UI

  • /knowledge — dropzone + URL input, source list with status badges, 3s polling.
  • /goals/new → /goals/[id] — goal form, then session cards with sequential locking (session N unlocks when N-1 completes), progress bar, and the final-test panel once all sessions are done.
  • /study/[sessionId] — a 3-panel layout: streaming notes · grounded chat with citation chips · MCQ quiz (idle→active→results with per-question feedback).
  • /super — cross-book chat; the thread_id is created once and stored in localStorage, never regenerated server-side.

Deep Dive

Evaluation & RAGAS

"Does it actually work?" is answered with a real benchmark. The two retrieval strategies (plus hybrid) are scored head-to-head with RAGAS on a 30-question golden set over a bundled Environmental Science textbook. The runner (backend/eval/run_ragas.py) deliberately bypasses the router and forces each strategy in turn — apples-to-apples.

The setup

  • Book: "OAI551 — Environment and Agriculture", a 58-page textbook with clear unit/section structure (exactly what exercises PageIndex). The original Biology 2e set targets a ~1,500-page book that isn't bundled.
  • Golden set: golden_qa_envsci.json — 30 Q&A matched to the bundled book (15 structural "deep" + 15 factual), each with a model-written ground_truth. Matching the set to the book is what makes all three metrics meaningful.
  • Metrics: Faithfulness (no hallucination), Answer Relevancy (on-topic), Context Precision (right chunks). Judge LLM + embeddings come from the same .env as the app.
  • Harness: for each question — force strategy → retrieve (top_k=5) → generate answer → 1.5s pacing. Ingestion is idempotent (reuses an already-ready book).

PageIndex wins faithfulness
  • Whole, coherent sections give the LLM more surrounding context to stay grounded in.
  • But those sections drag in unrelated material → lower precision/relevancy.
  • Slowest (one LLM tree-navigation call per query).
Vector wins relevancy + precision
  • Semantic chunk search returns tighter, more on-point passages with less noise.
  • ~700ms faster — no LLM at query time.
  • But less grounding context → higher hallucination risk.
⚗️
Hybrid gets the best of both (0.94 / 0.90 / 0.90) — it keeps PageIndex's grounding and nearly matches Vector's precision. That's the empirical case for shipping hybrid (or auto) as the default. The canonical record is backend/eval/results/comparison_3way.json.

Adaptive Learning

The feature that makes Scholar a tutor rather than a content generator. Three thresholds drive the whole progression:

65%
quiz pass — below inserts a remedial session
70%
final-test pass — marks goal complete
50%
weak-session flag on the final test

The remedial-insert flow (score < 65%)

1
Score (pure Python)
evaluate_quiz() compares answers to the stored correct_index — deterministic, no LLM, no way to game it. The session is marked complete with its score regardless.
2
Fetch session context fresh
handle_quiz_failure() re-reads session_number, topic, and goal context by UUID — never trusts stale numbers, which matters when multiple failures stack.
3
Generate one remedial session
The Adaptive Planner LLM produces a single targeted session focused on the weakest concepts of the failed topic, at the student's level.
✓
Atomic insert + renumber
In one transaction: shift every later session_number by +1, then insert the new session at failed_number + 1. The frontend shows an amber "Adaptive session added" banner.
🔒
Why atomic? A second failure on a later session could otherwise interleave inserts and corrupt the ordering. Doing the shift-and-insert in a single transaction makes repeated adaptation safe.

Key Design Decisions

The trade-offs worth defending in an interview — what was chosen, what was rejected, and why.

Two retrievers, not one
✓ Chose: PageIndex + Vector + router
✗ Rejected: vector-only RAG
Each strategy has a measured blind spot. The benchmark proves hybrid keeps PageIndex's 0.94 faithfulness while nearly matching vector's 0.92 precision. A single strategy can't do both.
Two storage tiers
✓ Chose: Postgres+pgvector (all data + checkpoints) / disk (blobs)
✗ Rejected: split relational data across multiple stores
Originally SQLite held relational state; migrated to a single PostgreSQL (with pgvector for embeddings + ivfflat index) accessed via SQLAlchemy 2.0 async ORM. The LangGraph AsyncPostgresSaver checkpointer lives in the same DB — one consistent, server-grade, async store. Trees and PDFs stay on disk as read-only blobs.
Native SSE, no library
✓ Chose: fetch + ReadableStream parser
✗ Rejected: EventSource / SSE lib
EventSource can't POST a JSON body or set headers, and pulling in a library for ~25 lines of well-specified parsing isn't worth the dependency. Returns a clean AbortController cleanup.
LangGraph only for chat
✓ Chose: checkpointer for conversations
✗ Rejected: model the whole app as a graph
Planning/quiz/notes are stateless one-shots — a graph would be ceremony. LangGraph earns its place exactly where state persistence matters: multi-turn chat surviving refreshes.
Pure-Python quiz scoring
✓ Chose: compare to stored correct_index
✗ Rejected: LLM-graded answers
Deterministic, free, instant, and ungameable. The correct_index is stored server-side and never sent to the client on generate.
Model-agnostic via .env
✓ Chose: one factory, every call
✗ Rejected: hardcoded provider SDK
Swap OpenAI→Anthropic→Ollama by editing .env. The same indirection makes the RAGAS judge provider-agnostic too — no separate eval config.

Known Weaknesses & Gaps

The honest list — knowing these (and how you'd fix them) signals engineering maturity in an interview.

eval Small benchmark
30 Q&A on a single 58-page book. Directional, not statistically tight (~±0.05–0.10/metric). Fix: 50–100 pairs across multiple books/domains.
security No auth
No users, sessions, or access control — single-tenant local app. Multi-user would need auth + per-user data scoping.
ux Polling, not push
Ingestion status and Notion export poll every 3s rather than using WebSockets/server-push.
ux Chat history on reload
History is checkpointed server-side by thread_id, but the frontend doesn't re-hydrate it on page load — a reload shows an empty panel.
retrieval Fixed top_k
top_k is hard-coded (8 notes / 5 chat / 8 super). Optimal k varies by book/domain; no sweep yet.
integration Notion not idempotent
Each export creates new pages; re-exporting duplicates rather than updating in place.
cost PageIndex index cost
~140–220 LLM calls to tree-index one book. One-time, but real money on large libraries; and large books inflate query-time navigation.
scale Single-process background tasks
Ingestion runs as in-process BackgroundTasks — fine locally, but a real deployment wants a job queue (Celery/RQ) for retries and concurrency.

Product & Ops
Why Postgres for everything?
Everything now lives in a single PostgreSQL database — relational tables (goals, sessions, quiz data, chat history, cumulative tests), the pgvector knowledge_chunks embeddings table (with its ivfflat cosine index), and the LangGraph AsyncPostgresSaver checkpointer. Data access goes through the SQLAlchemy 2.0 async ORM (asyncpg) with connection pooling. The project originally used embedded SQLite for relational state, but migrated to Postgres for a server-grade, async, scalable store: ORM-parameterised queries add a security boundary, connection pooling handles concurrency, and a single consistent datastore simplifies ops compared to keeping SQLite and Postgres in sync.
Why not model the whole app as a LangGraph graph?
Most agents are stateless one-shots — planning, quiz generation, note generation. Wrapping those in a graph is ceremony. LangGraph is used precisely where it pays off: multi-turn conversation persistence. The orchestrator builds a minimal graph with a single pass-through node just so the checkpointer has something to attach to.
How does chat survive a refresh?
The AsyncPostgresSaver checkpointer stores conversation state per thread_id in Postgres. Session chat uses thread_id = goal_id; the Super Agent uses a client UUID kept in localStorage. On each turn the agent loads prior messages from the checkpoint, appends, and writes back — no bespoke history table. (Caveat: the frontend doesn't yet re-hydrate that history on page load.)
Why a custom SSE parser instead of a library?
The browser's native EventSource can't issue a POST with a JSON body or custom headers, which the streaming endpoints need. The SSE wire format is ~25 lines to parse off a fetch ReadableStream, and doing it by hand returns a clean AbortController-based cleanup that wires straight into React effects.
What is PageIndex and how is it different from vector RAG?
PageIndex is structural, vectorless retrieval. At ingestion an LLM builds a hierarchical tree of the document (sections, summaries, page ranges); at query time another LLM reads that skeleton and picks which sections answer the question, returning whole coherent sections. Vector RAG instead chops the doc into fixed 600-token chunks and matches by embedding similarity. PageIndex preserves structure; vector preserves precision.
Why is hybrid the default, and what are the weights?
combined = 0.6·pageindex + 0.4·vector, de-duplicated by content hash. The benchmark shows PageIndex wins faithfulness (0.94) while vector wins precision (0.92) — a real trade-off. Hybrid inherits PageIndex's grounding and nearly matches vector's precision (0.94 / 0.90 / 0.90), so it's the best single default. auto goes further and routes per query.
How do you keep answers grounded (no hallucination)?
Three layers: (1) every answer is built only from retrieved chunks, and the system prompt enforces "answer only from the provided context"; (2) responses carry citations to source + page; (3) the Faithfulness RAGAS metric measures it — hybrid scores 0.94, meaning ~94% of claims are supported by the retrieved context.
Tell me about the PageIndex bug.
Classic silent-failure war-story. PageIndex retrieval returned zero chunks for almost every query — no errors, valid JSON, just useless. Two root causes: the builder passed Python True for options the library checks against the string 'yes' (so node text/summaries were never written), and the retriever read node.id while the library writes node_id. The takeaway: a RAG component can look healthy and still retrieve nothing — only evaluation catches it.
Is the 30-question benchmark enough?
It's directional, not definitive — ~±0.05–0.10 per metric at n=30 on one book. It's honest about that. The value is the relative comparison (the strategies were run apples-to-apples with the router bypassed) and the methodology, which generalizes: any book can get a matched golden set the same way.
How does adaptive learning actually trigger?
On quiz submit, pure-Python scoring computes a fraction. Below 0.65, handle_quiz_failure() generates one targeted remedial session and inserts it after the current one, atomically renumbering later sessions so stacked failures can't corrupt the order. The final test flags any session scoring under 0.50 as weak.
How would you make this multi-user / production-ready?
Add auth + per-user data scoping; move ingestion to a real job queue (Celery/RQ) for retries and concurrency; re-hydrate chat history on load; replace status polling with WebSockets; and expand the eval set to 50–100 Q&A across domains with CI regression gates.
How do I switch the model or run fully local?
Edit .env. Set LLM_PROVIDER=anthropic + a Claude model, or openai-compat with LLM_BASE_URL=http://localhost:11434/v1 for Ollama. The same change flows to chat, planner, notes, quiz, router, PageIndex navigation, vision, and the RAGAS judge — nothing is hardcoded.
What happens if PageIndex tree-building fails?
Graceful degradation. The builder logs a warning and returns None; ingestion still completes vector-only and the source becomes ready with pageindex_doc_id = NULL. The router reads that and routes the source to vector with no LLM call. Nothing breaks — you just lose structural retrieval for that one book.
How is observability handled?
When LANGCHAIN_API_KEY is set, every agent/LLM call is traced in LangSmith (strategy, latency, token cost) under project scholar-v2. Absent the key it's a silent no-op — no code paths change.
